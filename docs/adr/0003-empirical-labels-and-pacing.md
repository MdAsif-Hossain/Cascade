# ADR-0003 — Empirical labels, and pacing by tokens rather than requests

**Status:** Accepted
**Date:** 2026-08-14
**Phase:** 2 (intelligence)

## Context

The difficulty classifier needs a training label for each question. Two options were available.

**Proxy labels** — derive difficulty from something observable about the question: length, dataset of origin, whether it contains numbers. Free to compute, and indefensible: they describe what a question *looks like*, not what it costs to answer. A short question can be hard and a long one trivial.

**Empirical labels** — run every question through a real T1 model and a real T2 model, grade both against known-correct answers, and label by which tier first succeeded. Expensive in API calls, but the label *is* the routing decision the classifier is being asked to predict.

Three practical problems surfaced while building this.

**1. Pacing by requests does not work.** The first pilot ran four questions concurrently and lost 9 of 60 to exhausted rate-limit retries. Live response headers explain why: `llama-3.1-8b-instant` allows 14,400 requests/day but only **6,000 tokens/minute**. Request-rate pacing sails past a token limit, and reacting to a 429 is already too late — by then the quota is spent and every in-flight request is about to fail too.

**2. The question pool was too easy.** A 60-question pilot measured T1 accuracy per source: ARC-Easy 100%, GSM8K 92%, SciQ 83%, ARC-Challenge 73%, OpenBookQA 71%. An even split yields a pool that is roughly 86% T1 — a classifier could score 86% by always predicting T1 and learning nothing.

**3. Provider failures are not difficulty.** A question that returned a 429 or a 503 has no measured difficulty at all. Labelling it T3 would silently convert provider outages into training signal.

## Decision

**Empirical labels**, generated by `ml/label_empirical.py`, with three supporting decisions.

1. **A token-budget pacer** (`TokenPacer`) tracks estimated spend over a trailing minute and blocks before exceeding it, rather than discovering the limit through 429s. Estimates are generous and replaced with the provider's reported usage once known. The two labelling models sit on *different providers* — T1 on Groq, T2 on Gemini — so the stages meter separately and the run finishes in roughly half the wall time.

2. **The pool is weighted towards harder sources** — ARC-Challenge 400, GSM8K 300, OpenBookQA 300, ARC-Easy 120, SciQ 130. This changes the class balance, not the labels: each question's tier remains whatever the models actually achieve on it.

3. **Every response is cached to disk before anything else**, and questions with a provider error are **excluded** from the label file rather than labelled T3. The cache is append-only JSONL keyed by (model, question), so an interrupted run resumes for free and a re-run reproduces identical labels rather than resampling a non-deterministic model.

## Consequences

**Positive**

- The pacer eliminated the failure entirely: 0 errors across the full 1,250-question run, against 9 in 60 before it.
- The cache proved itself in practice — the run was interrupted mid-way and resumed with 531 responses intact, costing nothing.
- Labels are reproducible. Anyone with the cache file regenerates identical labels without spending a single API call.

**Negative**

- The run takes roughly 45 minutes of wall time, almost all of it waiting on the token budget. This is the floor imposed by a free tier and cannot be engineered away.
- Excluding provider-error questions shrinks the pool slightly and, in principle, non-randomly: a question is more likely to error if it is long, and long questions may be harder. The effect is small at the observed error rate but is a real, if minor, source of bias and is reported as such.

**Neutral**

- Weighting the pool towards harder sources means the label distribution does not represent the distribution of questions a real student would ask. Cost-reduction figures computed from this pool are therefore *conservative* — a realistic mix would be easier and route cheaper. The final report states this rather than presenting the number as a forecast.
- Grading accuracy caps label quality, so `ml/grading.py` is deliberately strict: when it cannot tell what the model chose, it grades the answer wrong rather than guessing. 32 tests cover the answer shapes models actually emit.
