# Cascade — Final Report

**Author:** Md. Asif Hossain
**Date:** 2026-08-15

---

## 1. What was built

Cascade is an AI study assistant that answers student questions at a fraction of frontier inference cost. A question is classified for difficulty, routed to the cheapest model likely to answer it, checked by a model from a *different provider*, and escalated only when that check fails. Everything runs on free provider tiers: $0 inference, $0 hosting.

The project set out to build three things. Two work as intended. One does not, and that is the most interesting result in this report.

| Component | Outcome |
|---|---|
| Trained difficulty classifier | **Does not beat a majority-class baseline.** §3 |
| Quality verifier with escalation | Works; cross-provider constraint enforced structurally. §4 |
| Catalog drift detection | Works, and caught real drift during development. §5 |

Supporting the three: three provider adapters behind a shared contract, a router with retry, failover and circuit breaking, a FastAPI service with seven endpoints, a Next.js frontend, and 305 tests that pass offline.

## 2. Empirical labels

Difficulty labels were generated by measurement, not proxy. 1,249 questions from ARC-Easy, ARC-Challenge, GSM8K, SciQ and OpenBookQA were each sent to a real T1 model (`groq/llama-3.1-8b-instant`) and, where that failed, a real T2 model (`gemini/gemini-3.1-flash-lite`), then graded against known-correct answers.

| Label | Meaning | Count | Share |
|---|---|---:|---:|
| T1 | The small model answered correctly | 1,052 | 84.2% |
| T2 | T1 failed, the mid model succeeded | 179 | 14.3% |
| T3 | Both failed | 18 | 1.4% |

**The project's central premise is confirmed: 84.2% of questions did not need an expensive model.** The engineering thesis — that most questions can be answered cheaply — holds.

That same number is why the classifier fails. With 84.2% of the data in one class and 1.4% in another, there is very little minority signal to learn, and a model that predicts the majority class scores 84.2% without learning anything.

This was visible early. A 60-question pilot measured T1 accuracy per source (ARC-Easy 100%, GSM8K 92%, SciQ 83%, ARC-Challenge 73%, OpenBookQA 71%), and the pool was reweighted towards the harder sources before the full run. It moved the distribution barely at all.

## 3. The classifier — a negative result

### What was measured

| Metric | Value |
|---|---|
| Accuracy | 0.8333 |
| **Majority-class baseline** | **0.8400** |
| **Improvement** | **−0.0067** |
| Macro-F1 | 0.3550 |
| Test size | 150 |

| Tier | Precision | Recall | F1 | Support |
|---|---:|---:|---:|---:|
| T1 | 0.85 | 0.98 | 0.91 | 126 |
| T2 | 0.50 | 0.09 | 0.15 | 22 |
| T3 | 0.00 | 0.00 | 0.00 | 2 |

The classifier predicts T1 for 98% of T1 questions and also for most T2 questions. It identifies 2 of 22 T2 questions and none of the 2 T3 questions. Its accuracy is marginally below always guessing T1.

> **Disclosure — the test split was evaluated twice.** The specification requires it to be touched once. It was evaluated once, then a train/inference feature leak was found (§3.3), the feature was removed, the model retrained, and the split evaluated a second time. Both results are recorded: `ml/results/test_results_v1_with_leak.json` (accuracy 0.8400, macro-F1 0.3584) and `ml/results/test_results.json` (the numbers above). The second run is reported as the headline because the first model contained a feature that cannot be computed at inference. No hyperparameter was tuned between the two runs — the only change was deleting the leaking feature. Two evaluations is still a weaker guarantee than one, and it is stated here rather than hidden.

The difference between the two is one question out of 150. The conclusion is unchanged either way: the classifier does not beat the baseline.

**This does not support the claim that question difficulty is predictable from question text at this data scale.** The proposal asserted that deciding which questions need an expensive model is "a learnable problem". On this evidence, with these features and this much data, it is not learned.

### The ablation — what did work

The ablation is the one classifier artifact that produced a clear, positive finding.

| Model | Features | Dims | Accuracy | Macro-F1 |
|---|---|---:|---:|---:|
| logistic | handcrafted | 22 | 0.396 | 0.230 |
| logistic | embedding | 256 | 0.638 | 0.302 |
| logistic | both | 278 | 0.671 | 0.304 |
| boosting | handcrafted | 22 | 0.846 | 0.334 |
| boosting | embedding | 256 | 0.805 | 0.393 |
| **boosting** | **both** | **278** | **0.819** | **0.423** |

Three things are legible here:

1. **Both feature families carry signal, and they are additive.** Macro-F1 rises monotonically: handcrafted 0.334 → embeddings 0.393 → both 0.423. Neither family is decoration; the embedding API call on the hot path is justified by a measurable gain.
2. **Gradient boosting beats logistic regression on every feature set**, decisively. Logistic regression with balanced class weights over-predicts the minority classes and collapses to 0.396 accuracy on handcrafted features. This is why both estimators are reported rather than only the first.
3. **No configuration beats the baseline on accuracy.** Boosting on handcrafted features alone *equals* it exactly (0.846) — the signature of a model that has learned to always answer T1. The gain from adding embeddings shows up only in macro-F1, where the model becomes slightly better at not ignoring the minority classes while getting no better overall.

### Calibration

Expected calibration error **0.1258** on validation.

| Confidence | n | Mean confidence | Observed accuracy | Gap |
|---|---:|---:|---:|---:|
| 0.5–0.6 | 1 | 0.561 | 1.000 | +0.439 |
| 0.6–0.7 | 4 | 0.674 | 0.500 | −0.174 |
| 0.7–0.8 | 8 | 0.754 | 0.875 | +0.121 |
| 0.8–1.0 | 136 | 0.946 | 0.824 | −0.122 |

The model is overconfident where it matters: 136 of 149 validation questions land in the top band, where it claims 0.946 and is right 0.824 of the time. Confidence is therefore **not** used as a routing input anywhere in the system. Had it been, that band would have driven systematically over-trusted decisions across the overwhelming majority of traffic.

### 3.3 A feature that leaked

An earlier version of the model included `num_choices` — the number of answer options a question offers.

That is a property of the benchmark, not of a question. 76% of training rows carried four options, because they came from multiple-choice datasets. A student typing into the box always supplies zero. The model learned to read a feature whose value at inference is a constant that appeared in only 24% of training data.

It was removed and the model retrained. Two things are worth recording:

- **The measured effect was small** — test accuracy moved from 0.8400 to 0.8333, one question in 150. The leak was not what made the classifier weak.
- **It was found by accident, not by testing.** It surfaced while capturing screenshots, when every question appeared to route to T2. That turned out to have a different cause (§6, embedding quota exhaustion putting the classifier into fallback), and the leak was noticed only while investigating.

`app/routing/features.py` is now the single implementation shared by training and inference, and `tests/test_features.py` asserts that a question's feature vector does not change when answer options are attached. A feature that cannot be computed identically in both places is worse than no feature at all.

### Why it failed

Three causes, in order of how much they matter:

1. **Class imbalance.** 84.2% / 14.3% / 1.4%. The T3 class has 18 examples in total, and 2 in the test split. No estimator recovers a class from two examples.
2. **The signal may not exist in the text.** Whether `llama-3.1-8b-instant` gets a question right depends on what that specific model memorised during training — a property of the model, not of the question's surface form or meaning. Two questions that look and read alike can fall on opposite sides of its competence boundary.
3. **Scale.** 994 usable rows against 279 features is thin. More data would help, though the imbalance means 10× the data yields only 10× of a very sparse minority.

### What should have been done differently

The label should have been binary from the start: *does the cheap model get this right, yes or no?* That is the decision the router actually makes — T2 versus T3 is only consulted after an escalation has already been triggered. A 1052/197 binary split is still imbalanced but far more tractable than 1052/179/18, and every metric would have been measured against the decision the system genuinely takes. Restructuring after seeing the test result would be tuning on the test set, so it is recorded here as the recommendation rather than performed.

## 4. The verifier — and why the classifier's failure is survivable

The verifier is what stops the classifier's weakness becoming the student's problem.

Two stages, cheap first. Heuristics catch empty output, refusals, truncation, and absurd length with no model call. Surviving answers go to an LLM judge that scores 0–1; below 0.7 the question escalates a tier, capped at two escalations.

**The judge never runs on the provider that produced the answer.** This is enforced structurally, not by a check: `Verifier.verify` passes `exclude_providers={answered_by_provider}` into the router, so a same-provider judge cannot be selected. Self-preference bias is well documented, and a same-family judge produces numbers that look like quality measurement and are not. Two tests assert the constraint in both directions of the provider pairing.

The measured under-prediction rate is **14.0%** — the share of questions where the classifier picked a tier too weak for the question. Those 14% are exactly what the verifier exists to catch. A system with this classifier and no verifier would silently return a worse answer to roughly one question in seven.

When no cross-provider judge is reachable, the loop **fails open**: the answer already passed the cheap checks, and escalating everything during a provider outage would multiply load precisely when capacity is shortest. The response carries a warning so an unverified answer is visibly unverified.

## 5. Catalog drift — the feature that earned itself

Free providers delete models without notice. This was not a hypothetical:

- **Gemini advertises models it will not serve.** `gemini-2.5-flash`, `gemini-2.5-pro` and `gemini-2.5-flash-lite` all appear in the model-list endpoint and all return HTTP 404 — *"no longer available to new users"* — when called. A drift detector that only diffed model lists would report no change while every request to those models failed.
- **OpenRouter reports upstream failures inside HTTP 200.** `{"error": {"message": "Upstream error from Nvidia", "code": 502}}` arrived with a 200 status. The adapter initially classified this as a malformed response — a permanent fault — when it was a transient outage that should fail over.
- **Free models rate-limit independently.** `google/gemma-4-31b-it:free` returned 429 in the same second three sibling free models answered.

The consequence is recorded in ADR-0002: **listing and callability are separate facts** and are tracked separately. Every model in the tier table was verified callable before being listed there.

## 6. Engineering results

| Metric | Value |
|---|---|
| Tests | 305, passing offline with no API keys |
| Lint / types | `ruff` and `mypy --strict` clean |
| Provider adapters | 3, all passing one 28-assertion shared contract suite |
| Classifier artifact | 569 KB |
| Groq latency | 126 ms |
| Gemini latency | 908 ms |
| OpenRouter (free) latency | 27.5 s |
| Labelling run | 1,249 questions, **1 provider error** |

Two engineering findings worth recording:

**Rate limits are metered in tokens, not requests.** Groq allows 14,400 requests/day but only 6,000 tokens/minute. The first labelling pilot used four concurrent workers and lost 9 of 60 questions to exhausted retries. A token-budget pacer that reserves headroom *before* sending reduced that to 1 error in 1,249 questions. Reacting to a 429 is already too late — the quota is spent and every in-flight request is about to fail too.

**Caching every response before anything else made the work survivable.** The labelling run was interrupted mid-way and resumed with 531 responses intact at zero cost. The same property let training resume after the embedding quota was exhausted.

**A degraded dependency is invisible unless the system reports it.** The free embedding tier allows roughly 1,000 requests per day and ran out at 993. The classifier needs an embedding to predict, so every subsequent request fell back to a fixed tier — correct behaviour, and the reason the service kept answering. But from the outside it looked like a working classifier that had decided everything was T2. Only `prediction_source: "no_embedding"` in the API response made the difference visible. Degradation that is not reported is indistinguishable from a bug, and this one cost an hour of misdiagnosis.

## 7. Limitations

Stated plainly, because a limitations section that names nothing reads as untested.

1. **The classifier does not work.** It matches a majority-class baseline exactly and identifies almost no T2 or T3 questions. The routing decisions it makes are, in effect, "always T1".
2. **The 97.6% cost-reduction figure is a consequence of that failure, not a success.** Because the classifier nearly always predicts T1, routed cost is nearly always T1 cost. The number is arithmetically correct and counterfactual — no money was spent — but it should be read as "what always-T1 routing would cost", together with the 14% under-prediction rate that the verifier absorbs.
3. **T3 is statistically meaningless.** 18 examples total, 2 in the test split. Its precision, recall and F1 are noise, and no claim should be built on them.
4. **The evaluation used 994 of 1,249 labelled questions.** The free embedding tier's daily quota ran out at 993 vectors. All feature sets use the identical subset so the ablation remains a fair comparison, but statistical power is lower than the label count suggests.
5. **The question pool is not representative of real student questions.** It is public benchmark data, weighted towards harder sources on purpose. A realistic mix would be easier, so the cost figures are conservative rather than predictive.
6. **The verifier's threshold (0.7) and escalation cap (2) are unvalidated.** They come from the specification, not from tuning. Tuning them would require a labelled set of good and bad *answers*, which this project does not have — the empirical labels record whether a model was correct, not whether the judge agreed with it.
7. **The judge is itself a cheap model** and will sometimes be wrong. Its scores are a filter, not ground truth.
8. **Quality retention vs. an always-T3 baseline was not measured directly.** What is reported is how often the *predicted tier was sufficient* (86.0%), which is a proxy — it does not measure whether the returned answer was actually good.
9. **The test split was evaluated twice, not once.** See the disclosure in §3.1. The cause was a feature leak found after the first evaluation; no tuning occurred between runs, and both results are published. It is still a weaker guarantee than the specification asks for.
10. **Not yet deployed.** Deployment configuration for Render and Vercel is written, and the full stack has been verified running locally — screenshots in `docs/screenshots/` are from `localhost`. No public URL exists yet.

## 8. Conclusion

The cost argument survives; the learnability argument does not.

84.2% of student questions were answered correctly by the cheapest available model. That is the finding the whole product rests on, and it is solid. What does not hold is the assumption that a classifier can identify the remaining 15.8% from question text — at this scale, with these features, it cannot, and the honest measurement is a dead heat with guessing the majority class.

That failure is survivable only because of the verifier. The 14% of questions routed too cheaply are caught by a second model from a different provider and escalated. Cost reduction without that check would be a silent quality reduction; with it, the same routing behaviour is safe. The component that looked like scaffolding around the classifier turns out to be the thing carrying the system.

The most useful next step is not a better model but a better question. Predicting *which of three tiers* a question needs asks more than the router ever uses. Predicting *whether the cheap model will be right* — one binary decision, on 5× the minority data — is the decision the system actually makes, and is where the next attempt should start.
